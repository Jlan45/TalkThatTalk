TalkThatTalk 路由引擎与上下文前缀亲和架构设计

系统性修复多 Provider 同模型路由中的权重失真、回退缺失与跨协议死路问题，并建立兼容异构 Coding Agent（Claude Code、Codex CLI、OpenCode、Cline/Roo、Cursor 及无头 SDK）的多级会话与前缀亲和路由体系。

01设计目标与现状问题清单

问题一 多 Provider 同模型路由缺陷
  • 权重倾斜与突刺：weighted_ring 连续展开造成突刺；协议分层与 AccessPolicy 过滤在选点之后执行，导致被跳过节点之后的紧邻节点吃掉大量偏移流量。
  • Exact 无法回退 Wildcard：若私有 Provider 命中 exact 池但当前用户无权访问，直接报 403，不会降级到全局 "*" 池。
  • 跨协议死路未跳过：Tier 2 未校验 ttt-protocol 是否支持翻译，选中后直接报错中断，不尝试后续候选。
  • 重试与冷却不足：max_attempts 只看首节点 max_retries；5xx/连接失败不触发冷却；/v1/models 误推进轮询 cursor。
问题二 同前缀上下文 Prompt Cache 击穿
  • 无任何会话/前缀亲和：当前只扫描 "model" 字段，每次请求无条件 cursor.fetch_add(1) 轮询切换 Provider。
  • 同 Provider 多 Key 击穿：ApiKeyPool::acquire 同样每次无条件轮询切 Key，按账号/Key 隔离缓存的上游仍会 Cache Miss。
  • 异构 Agent 头不统一：Codex 发 session_id、Claude Code 放 metadata.user_id、OpenAI 用 prompt_cache_key、各类 IDE Agent 用不同的 x-*-id，必须统一抽象并支持前缀兜底。

03多 Agent 异构 Session 标识适配方案

affinity.rs

不同 Coding Agent 和 SDK 传递会话标识的方式完全不统一：有的走裸 Header（如 Codex 的 session_id），有的嵌在 Body 的 metadata.user_id（如 Claude Code），有的走官方 prompt_cache_key，还有的完全不传。设计上采用四级瀑布提取 + 自定义 Header 扩展 + 反模式黑名单。

四级提取优先级（Waterfall）

Tier 0
强状态 Body
previous_response_id / cachedContent

强依赖创建该状态的上游实例，跨 Provider 会直接 404/400，因此优先级高于普通会话头。

Tier 1
Session Header
O(1) 零 Body 解析，支持用户前置自定义头

内置匹配顺序（可在 routing.session_headers 扩展），校验长度 4..=256 且非占位脏值：

x-ttt-session-id session_id conversation_id x-session-id x-conversation-id x-thread-id x-claude-code-session-id x-opencode-session-id x-cline-task-id x-roo-task-id x-cursor-session-id x-chat-id x-client-session-id
Tier 2
Body 原生字段
SIMD memchr::memmem 轻量扫描（无需完整 DOM 解析）

按序扫描 prompt_cache_key → conversation → metadata.user_id（对 Claude Code 自动抽取 session_<uuid>）。

Tier 3
前缀指纹兜底
无显式标识时的通用上下文前缀指纹

仅在候选数 > 1 且 Tier 0~2 全未命中时触发；流式读取到 system + 首条 user 消息即提前终止。

反模式黑名单（严禁作为 Session 亲和键）：
x-request-id x-correlation-id traceparent x-stainless-* authorization user-agent x-forwarded-for

前 4 个为单次请求唯一 ID（会导致每次哈希变化、亲和失效）；后 3 个粒度过粗（同一用户并发开多个 Agent 时会全压到单一 Provider，破坏负载均衡）。

04上下文前缀指纹与命名空间隔离

为什么是 System + 首条 User 消息？
  • 不能哈希全部 messages：多轮对话每轮都会追加新消息，哈希每轮都变，彻底失去粘性。
  • 不能只哈希 system：同一 Agent（如 Cursor/Cline）的所有并发会话共享相同的 System Prompt，会导致全部流量打到单个 Provider。
  • 最优解：CanonicalPrefix = System/Instructions + FirstUserMessage[..4KB]。同一会话第 1 轮到第 50 轮前缀完全不变（100% 粘性）；不同会话首条用户输入不同（自然均衡散列）。
  • 短消息豁免：有效前缀长度 < 64 bytes（如 "hi"）跳过亲和，走无状态平滑轮询。
四协议规范化提取规则
  • OpenAI Chat：合并所有 role == "system" | "developer" 文本 + 首条 role == "user" 文本。
  • Anthropic Messages：system（兼容 string / text block 数组，忽略 cache_control）+ 首条 user 文本。
  • OpenAI Responses：instructions + input（字符串或首条 user 文本）。
  • Gemini：systemInstruction + contents[0] 文本。

命名空间隔离哈希（零新依赖，复用 sha2）

AffinityHash = SHA256(
    owner_user_id_or_global || 0x00 ||
    requested_model         || 0x00 ||
    source_tag              || 0x00 ||
    normalized_raw_key
)[0..8] as u64

隔离收益：① 同一 Agent 会话内，主模型（如 claude-opus-4）与子任务模型（如 claude-haiku-4）拥有独立哈希空间；② 不同租户之间绝不碰撞。

05多 Provider 同模型路由重构

Filter-Before-Select
1. 前置过滤 + Exact→Wildcard

在选点前先按 AccessPolicy 与 ttt_protocol::supports_translation() 过滤候选。精确池为空（被权限过滤或全故障）时自动降级到去重后的 wildcard("*") 池；仅当两池原始非空且全被权限拦截时才返回 403。

2. 有亲和 → Weighted HRW

在每个优先级桶内，对节点 $i$ 计算确定性得分： score = -ln(u_i) / weight_i（升序）。任意过滤子集内严格满足选中概率 w_i / Σw，节点冷却/上下线时仅迁移受影响会话（极小扰动）。

3. 无亲和 → 预计算 Smooth WRR

构建 RoutingTable 时用 Nginx SWRR 预生成交错序列（如 [A,A,B,A,A,A]），消除连片突刺；同时为 /v1/models 提供只读可见性检查 has_accessible_node()，不再污染游标。

四级优先级分桶（Exact 池整体优先于 Wildcard 池）

Bucket 1

健康 + 原生协议
未冷却、Quota 正常，零拷贝透传

Bucket 2

健康 + 可翻译
已校验 supports_translation == true

Bucket 3

冷却/耗尽 + 原生
429/5xx 冷却或 Quota Exhausted 兜底

Bucket 4

冷却/耗尽 + 可翻译
最后兜底候选

实时模拟

假设同模型 claude-sonnet-4 配置了 3 个 Provider：Node A（权重 10，仅支持 OpenAI）、Node B（权重 1，原生 Anthropic）、Node C（权重 1，原生 Anthropic）。现在模拟 1,200 个独立 Anthropic 会话 请求进来，观察 B 与 C 之间的流量分配：

旧实现（线性偏移扫描）

当游标落在 A(w=10) 时，A 掉入 Tier 2，线性扫描永远先碰到 B，导致 B 吃掉 11/12 的流量！

新设计（Filter-Before-Select + Weighted HRW）

先分桶再在桶内做加权一致哈希：B 与 C 严格按 1:1 分配，且同一会话多轮 100% 命中同一节点。

07防抖动软粘性、多 Key 二级亲和与熔断冷却

防抖动 Soft-Sticky Failover 缓存

正常命中 HRW 首选时零写锁。仅当发生 Failover（实际成功节点 ≠ HRW 主选节点）时，将 affinity_hash → actual_upstream 写入有界分片缓存（上限 4096，TTL 300s 匹配 Prompt Cache 生命周期）。避免主节点 30s 冷却恢复后立刻切回导致备节点缓存失效。

二级亲和 ApiKeyPool 槽位绑定

ApiKeyPool::acquire_with_affinity(Option<u64>) 在有亲和哈希时以 mix64(h) % len 为起点选第一个未冷却 Key 槽位；无亲和时保持轮询。防止单 Provider 多 Key 打散上游 Prompt Cache。

熔断与重试 5xx 退避 & Quota 联动

max_attempts 取候选池最大 max_retries + 1，不再被首节点 0 重试锁死；连续 502/503/504 或连接错误触发指数退避短冷却（3s→6s→12s→...→60s），成功即清零；联动 QuotaStatus::Exhausted 自动降级。

08配置扩展与可观测性

100% 向后兼容 
[routing]
# 是否开启会话与前缀亲和路由（默认 true）
affinity_enabled = true

# 自定义额外 Session Header 列表（优先于内置主流 Agent 头列表）
# 内置已包含: x-ttt-session-id, session_id, conversation_id, x-session-id,
# x-conversation-id, x-thread-id, x-claude-code-session-id, x-opencode-session-id,
# x-cline-task-id, x-roo-task-id, x-cursor-session-id, x-chat-id, x-client-session-id
session_headers = []

# 无显式 Session Header/Body 字段时，是否回退到上下文前缀指纹（默认 true）
prefix_fallback_enabled = true
prefix_max_bytes = 4096
prefix_min_bytes = 64

# Failover 后备节点的软粘性保持时间（秒，默认 300s 匹配 Prompt Cache TTL）
sticky_failover_ttl_secs = 300

# 5xx / 连接错误的基础短冷却时间（秒，指数退避上限 60s）
failure_cooldown_base_secs = 3

# 是否联动 Quota 监控降级已耗尽额度的 Provider
quota_aware = true
新增可观测性响应头：除已有的 x-ttt-upstream 外，新增 x-ttt-affinity-source（如 header:session_id、body:prompt_cache_key、body:claude_metadata、prefix_hash、none），方便直接验证各 Agent 路由是否命中会话亲和。
